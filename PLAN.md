# 🚀 Space Station R (SSR) — План разработки многопользовательской 2D-песочницы на Rust

> **Назначение документа:** Этот файл — единый источник правды (Single Source of Truth) для проекта. Вставляйте его целиком в контекст ИИ в начале каждой рабочей сессии. Документ структурирован так, чтобы ИИ мог выполнять задачи по одной, не ломая архитектуру.
>
> **Референс:** Space Station 14 (Robust Toolbox, C#) — но пишем с нуля на Rust.
>
> **Нейминг:** репозиторий — `space-station-r`, крейты — `ssr-core`, `ssr-protocol`, `ssr-server`, `ssr-client`.

## 1. Контекст проекта (читать перед каждой сессией)

**Что мы делаем:** Многопользовательская 2D-песочница в духе Space Station 14: игроки на космической станции, роли, строительство, симуляция систем, раунды с целями.

**Ключевые ограничения:**

- Сервер-авторитарная модель (сервер решает всё, клиент только отправляет ввод и отображает состояние).
- НЕ lockstep-детерминизм, а репликация состояния (дельты).
- Масштаб: 1 сервер до ~100 игроков, мир на чанках.
- Клиент и сервер — отдельные бинарники из одного workspace, общий код — в общей крейте.

**Правила работы с ИИ:**

1. Перед изменением кода — прочитай разделы 2, 3, 4, 6 этого документа.
2. Выполняй ТОЛЬКО текущую задачу из дорожной карты. Не реализуй фазы наперёд.
3. После выполнения задачи обнови PROGRESS.md (поставь `[x]`).
4. Не меняй архитектурные решения (раздел 3). Если изменение необходимо — предложи его отдельным сообщением, не применяй молча.
5. Весь код должен компилироваться: `cargo build --workspace` и проходить `cargo clippy -- -D warnings`.
6. Не используй `unwrap()` и `panic!()` в коде сервера. Только `Result` + `thiserror`.

## 2. Технологический стек

> ⚠️ Версии проверить на crates.io на момент старта — зафиксировать в Cargo.toml и не обновлять мажорные версии без обновления этого документа.

| Назначение | Крейт | Примечание |
|---|---|---|
| Движок | `bevy` (последняя стабильная) | ECS, рендеринг, ввод, аудио |
| Физика 2D | `avian2d` | FORK bevy_xpbd, нативно под Bevy ECS. Альтернатива: `bevy_rapier2d` |
| Сеть | `lightyear` | Репликация, клиент-сервер, предсказание. Альтернатива: `bevy_renet` (проще, меньше фич) |
| Сериализация | `serde` + `postcard` | Компактный бинарный формат для сети |
| Карты/генерация | `noise`, `ndarray` | Процедурная генерация, сетки тайлов |
| Отладочный UI | `bevy_egui` | Инспектор сущностей, консоль сервера |
| Ошибки | `thiserror`, `anyhow` | thiserror в библиотеках, anyhow в бинарниках |
| Логирование | `tracing` + `tracing-subscriber` | Единый логгинг клиент+сервер |
| Сохранение | `serde` + `ron` | Конфиги и карты в формате `.ron` |

**Зафиксированные версии на старт (03.10.2026):** `bevy = "0.19.1"`, `lightyear = "0.30.1"` (собран под bevy 0.19; подтверждён выбор основного стека §2). У lightyear включены только фичи текущих фаз (`std, client, server, udp, raw_connection`) — `replication/prediction/interpolation` добавляются в T1.3+ (их системы требуют инфраструктуры репликации и паникуют без неё). Остальные крейты фиксируем в момент подключения соответствующей фазы.

## 3. Архитектурные решения (ADR — не менять без обсуждения)

| # | Решение | Обоснование |
|---|---|---|
| ADR-1 | Workspace из 4 крейтов: `core`, `protocol`, `server`, `client` | Разделение логики; сервер собирается headless без графики |
| ADR-2 | ECS везде: компоненты — чистые данные, системы — чистая логика | Единый стиль Bevy, параллелизм бесплатно |
| ADR-3 | Сервер-авторитарность: физика, урон, крафт, экономика — только на сервере | Защита от читов, единое состояние |
| ADR-4 | Репликация дельт, не снапшотов: шлём изменения компонентов, интерес-менеджмент по чанкам | Сеть для ~100 игроков |
| ADR-5 | Мир = сетка тайлов, чанк 32×32 тайла | Как в SS14/SS13; тайл — минимальная единица строительства |
| ADR-6 | Прототипы контента в `.ron`-файлах (предметы, рецепты, роли), не в коде | Контент добавляют без перекомпиляции; ИИ легко генерирует контент |
| ADR-7 | ID сущностей синхронизируются, клиент хранит маппинг ServerEntity → ClientEntity | Основа репликации |
| ADR-8 | Без плавающих точек в логике сетки (позиции тайлов — `IVec2`), float только для рендера и физики | Стабильность синхронизации |

## 4. Структура репозитория

```text
space-station-r/
├── Cargo.toml               # workspace
├── PROGRESS.md              # чеклист прогресса — ИИ обновляет его
├── PLAN.md                  # этот документ
├── assets/
│   ├── sprites/             # спрайты (стартовый набор — из сборки mini-station-goob)
│   ├── maps/                # карты станции в .ron
│   └── prototypes/          # предметы, роли, рецепты в .ron
├── crates/
│   ├── core/                # компоненты, события, игровая логика (общая)
│   │   └── src/
│   │       ├── components/  # Position, Health, Inventory, Item...
│   │       ├── events/      # DamageEvent, InteractEvent...
│   │       ├── systems/     # чистые системы над компонентами
│   │       └── prototypes/  # загрузка .ron-прототипов
│   ├── protocol/            # сетевые сообщения, версионирование протокола
│   ├── server/              # headless-сервер: авторитарная логика, репликация
│   └── client/              # Bevy-клиент: рендер, ввод, предсказание
└── tests/                   # интеграционные тесты
```

Зависимости внутри workspace: `client` и `server` зависят от `core` и `protocol`. `core` не зависит ни от кого. `protocol` зависит только от `serde`.

## 5. Дорожная карта

### Фаза 0 — Фундамент (задачи T0.*)

- **T0.1. Инициализация workspace.** Создать 4 крейта по разделу 4. Настроить cargo workspace, rustfmt.toml, уровень warnings deny в CI.
  Критерий: `cargo build --workspace` собирает пустые крейты.
- **T0.2. Hello Bevy.** В client: окно 1280×720, тёмный фон, спрайт в центре, движение стрелками/WASD.
  Критерий: окно запускается, спрайт двигается, 60 FPS.
- **T0.3. Headless-сервер.** В server: Bevy MinimalPlugins, тик-рейт 20 TPS (fixed timestep), лог каждого тика через tracing.
  Критерий: `cargo run -p ssr-server` работает и логирует тики.
- **T0.4. CI (GitHub Actions).** Сборка, clippy, тесты на каждый PR.
  Критерий: PR без зелёного CI нельзя мержить.

### Фаза 1 — Сетевой каркас (задачи T1.*)

- **T1.1. Протокол.** В protocol: enum ClientMessage (Connect, Input, Interact) и ServerMessage (Welcome, WorldState, EntityDelta, Event). Версия протокола — константа, несовпадение = отказ соединения.
  Критерий: round-trip тест: сериализация → десериализация → равенство.
- **T1.2. Подключение.** Клиент подключается к серверу (127.0.0.1:7777), получает Welcome со своим EntityId, сервер видит игрока в списке.
  Критерий: 2 терминала: сервер + клиент, в логе сервера «Player connected».
- **T1.3. Репликация позиций.** Одна сущность-куб двигается на сервере по вводу клиента; позиция реплицируется клиенту через дельты.
  Критерий: движение куба в клиенте повторяет сервер с задержкой < 200 мс локально.
- **T1.4. Interest management.** Сервер шлёт только сущности в чанках в радиусе 2 чанков от игрока.
  Критерий: тест: 1000 сущностей на сервере, клиент получает < 100.

### Фаза 2 — Мир и тайлы (задачи T2.*)

- **T2.1. Тайловая карта.** core: компонент Tilemap, чанки 32×32, типы тайлов (пол, стена, космос) из .ron-прототипа. Рендер чанков в клиенте.
  Критерий: тестовая карта 128×128 рендерится, скролл камеры по краям.
- **T2.2. Физика и коллизии.** avian2d: стены — статические коллайдеры, игрок — динамическое тело, движение с коллизиями.
  Критерий: нельзя пройти сквозь стену; позиция подтверждается сервером.
- **T2.3. Загрузка карты из файла.** Формат .ron: список чанков, тайлов, спавн-точек. Сервер грузит карту, реплицирует видимое клиенту.
  Критерий: изменение .ron меняет карту без перекомпиляции.
- **T2.4. Спавн игроков.** Несколько клиентов — каждый спавнится на своей точке, видят друг друга.
  Критерий: 3 клиента, все видят 3 персонажа и их движение.

### Фаза 3 — Взаимодействие (задачи T3.*)

- **T3.1. Система взаимодействия.** Клик по сущности/тайлу → InteractEvent на сервер → серверная логика → дельта клиенту. Радиус взаимодействия 1.5 тайла.
  Критерий: клик по двери открывает/закрывает её у всех клиентов.
- **T3.2. Инвентарь.** Компонент Inventory (слоты 7×4), предметы — сущности. Взять/положить/переложить. UI слотов в клиенте (bevy_egui → потом bevy_ui).
  Критерий: перетаскивание предмета между инвентарями двух игроков синхронизируется.
- **T3.3. Строительство/разрушение.** Стены строятся из предметов-материалов, разрушаются инструментами. Тайл меняется на сервере, реплицируется.
  Критерий: построенный одним игроком стена видна и «твёрдая» для всех.
- **T3.4. Контейнеры.** Ящики/шкафы как сущности с инвентарём, открытие по взаимодействию.
  Критерий: предмет из ящика доступен в UI при открытии, скрыт при закрытии.

### Фаза 4 — Игровые системы (задачи T4.*)

- **T4.1. Здоровье и урон.** Health, источник урона, смерть → возврат на спавн. Лог событий урона в лог сервера.
- **T4.2. Роли.** Прототип роли в .ron: название, стартовый инвентарь, доступы. Минимум: ассистент, инженер, предатель (антагонист с целью).
- **T4.3. Симуляция атмосферы (lite).** На тайлах: давление/O₂ по чанкам, диффузия между тайлами, пробой в космос = урон. Упрощённая модель — газы как числа на тайле.
- **T4.4. Электрика (lite).** Генератор → кабели (тайлы-провода) → потребители (двери, свет). Аптайм/энергобаланс.
- **T4.5. Цели раунда.** Таймер раунда, условия победы для экипажа и антагонистов, экран итогов.

### Фаза 5 — Контент и полировка (задачи T5.*)

- **T5.1.** Первая полноценная карта станции (медотсек, инженерный, бар, мостик) — сгенерировать ИИ по шаблону, доработать вручную.
- **T5.2.** 30+ предметов, 10+ рецептов крафта — все в .ron.
- **T5.3.** Спрайты и звуки (временные — CC0 из Kenney/OpenGameArt, заменить позже).
- **T5.4.** Меню, настройки, экран подключения по IP, список серверов.
- **T5.5.** Админ-команды сервера (телепорт, спавн предмета, кик).

### Фаза 6 — Тестирование и релиз (задачи T6.*)

- **T6.1.** Нагрузочный тест: 50 ботов-клиентов, замер TPS сервера и трафика.
- **T6.2.** Закрытая альфа с сообществом (форк «Мини-станции» — ядро тестеров).
- **T6.3.** Профилирование (tracing-chrome, criterion для бенчей), исправление топ-5 узких мест.
- **T6.4.** Публичная сборка: Steam/Itch.io или открытый сервер + лаунчер.

### Фаза 7 — Полное соответствие сборке SS14 (доработка, запрос владельца 04.10.2026)

Цель фазы: «всё 1 в 1 как в SS14» по тем местам, где ещё есть расхождения.
Правило работ прежнее: **сначала изучить сборку субагентами, потом делать**;
каждая задача закрывается скриншот-сверкой с эталоном (или точным логом).

- **T7.1. Свет и тени 1:1 (главное).** Сейчас карта света считается на CPU по
  тайлам (BFS от ламп, размытие всей карты, «протечка» света на стены по
  максимуму соседей) — визуально это расходится с движком: мягкость теней не
  та, свет виден сквозь стены/углы. Надо повторить модель движка: полярная
  карта теней + VSM/PCF (или её точный CPU-эквивалент), правило освещения
  стен, `softness`, блюр, применение карты к миру шейдером. Что именно менять —
  из спецификации субагента (отчёт от 04.10). Критерий: скриншоты тёмной
  комнаты/коридора рядом с эталонными кадрами SS14 совпадают по яркости зон,
  свет не проходит через стены и углы, стены видны с правильной яркостью.
- **T7.2. Скроллбары и списки.** Полоса прокрутки как в теме SS14 (текстуры
  `scrollbar_*`, толщина/цвета из темы), с перетаскиванием граббера и
  правильным шагом колеса. Куда: спавн-меню, окно внешности, окно хранилища,
  список мёртвых/телепорта (если есть). Числа — из отчёта субагента.
- **T7.3. Внешность: превью и маркинги.** В SS14 в редакторе есть панель
  превью куклы с поворотом (`SpriteRotateLeft/Right`) и вкладка маркингов
  (`MarkingPicker` — татуировки и прочее, кроме волос/бороды). Добавить превью
  в окно (своя кукла уже служит превью — вынести в панель с поворотом) и
  слой маркингов на тело (категории из `human_markings`/ассетов).
- **T7.4. Мелочи соответствия:** сортировка спрайтов мира по Y (сейчас
  документированное расхождение), ресайз чата, полный список строк
  спавн-меню с прокруткой (снимается T7.2), «последний апстрим»-строка
  в лобби (уже сделана).
- **T7.5. Профилирование (T6.3) — после T7.1:** карта света и UI — главные
  кандидаты; бенчи criterion на свет, замер FPS в тёмной/светлой зоне.

## 6. Конвенции кода (обязательны для ИИ)

```rust
// Именование
// - Системы:      fn movement_system(...)
// - Компоненты:   struct Health { current: u32, max: u32 }   (только данные)
// - События:      struct DamageEvent { target: Entity, amount: u32 }
// - Ресурсы:      struct GameConfig { ... }

// Правила:
// 1. Компоненты не содержат методов с логикой — логика в системах.
// 2. Системы общаются ТОЛЬКО через события, не через прямые запросы
//    к чужим сущностям без необходимости.
// 3. Вся сетевая логика — в protocol/server/client, core не знает о сети.
// 4. Все публичные API crates/core документированы: /// doc comment.
// 5. Тест на каждую чистую систему: #[cfg(test)] в том же файле.
// 6. Ошибки: thiserror в core/protocol, anyhow на верхнем уровне бинарников.
```

**Стратегия тестирования:**

- Юнит-тесты чистых систем (инвентарь, атмосфера — детерминированные, без Bevy App).
- Интеграционный тест сети: сервер + клиент в одном процессе через каналы, проверка репликации.
- Бенчмарки criterion на систему атмосферы и сериализацию дельт.

## 9. Ключевые риски и их обработка

| Риск | Симптом | План Б |
|---|---|---|
| lightyear не тянет наш масштаб | Лаги > 10 игроков | Даунгрейд на bevy_renet + собственная репликация (T1.1–T1.4 уже дают фундамент) |
| Атмосфера слишком тяжёлая | TPS сервера падает | Считать газы только в активных чанках, диффузию раз в N тиков |
| Rust тормозит разработку контента | Фаза 5 буксует | Усилить ADR-6: весь контент — данные, ИИ генерирует пачками |
| Физика недетерминированна | Рассинхрон позиций | Убедиться, что физика только на сервере (ADR-3), клиент — чистый наблюдатель |
